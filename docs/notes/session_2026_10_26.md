## What we worked on

### 1. Lakehouse coverage visualization app (PR #30)

Built a Streamlit app at `src/tractatus/app/coverage.py` that reads from
`~/.tractatus/catalog_ledger.db` and visualizes what data is in the lakehouse.

**Launch:**
```bash
tractatus app coverage
# or
tractatus app coverage --port 8502 --ledger /path/to/ledger.db
```

**Features:**
- Three inline dropdowns: Table (defaults to `options`), Provider (defaults to `schwab`),
  Symbol (optional, `All` shows all symbols)
- Calendar heatmap — x=day of month, y=month (YYYY-MM), one heatmap per (table, provider)
- Cell color semantics:
  - **Gray** (`#6B7280`): weekend
  - **Light red** (`#FECACA`): past weekday with no data
  - **Near white** (`#F8FAFC`): future date
  - **Teal gradient** (`#2DD4BF` → `#0d4f4a`): data present, intensity scales with `row_count`
    (brighter = fewer rows, darker = more rows)
- 2px gaps between cells for readability
- Hover tooltip shows actual date, status, and row count
- Summary table below heatmap: symbol, date range, total days, cached days, % cached, gap count
- Gap detection uses `pd.bdate_range` (business day approximation)
- `@st.cache_data(ttl=300)` — data reloads every 5 minutes on auto-rerun

**Theme:** Defined in `.streamlit/config.toml` using `[theme.light]` / `[theme.dark]`
(not `[theme]`) which preserves Streamlit's System/Light/Dark toggle in v1.66+.
See `docs/notes/ui_color_palette.md` for the full color role table.

**Key implementation notes:**
- Plotly colorscale positions are normalized: `position = (z + 1) / 2` with `zmin=-1, zmax=1`
- Defining a single `[theme]` in config.toml suppresses Streamlit's theme toggle entirely —
  must use `[theme.light]` + `[theme.dark]` to keep it visible
- `published_artifacts` had 13,598 rows across all tables when we built this — no backfill needed

### 2. `_TABLE_GRAIN` bug fix in publisher (PR #31)

`publisher.py` `_TABLE_GRAIN` mapped `order_book` to `"sampled_at"` as the date column
for Iceberg scan filtering in `cache_artifacts`. The order book schema has no `sampled_at`
column — it uses `received_at`.

**Fix:**
- Changed `order_book` entry to `"received_at"` in `_TABLE_GRAIN`
- Changed `cache_artifacts` to derive `sample_date` from `date_col` (the table's configured
  date column) rather than hardcoding `"sampled_at"`, so all tables work correctly

### 4. `received_at` vs `sampled_at` naming decision

The ingestion-time column is named differently across table types — intentionally:

| Tables | Column | Meaning |
|---|---|---|
| options, fundamentals, candles | `sampled_at` | When the sample/batch was fetched from Schwab |
| order_book, level_one | `received_at` | When Tickrake's streaming collector received the event (`Time.now.utc`) |

`received_at` is a **Tickrake concept**, not a Schwab field. Schwab's order book feed only
provides `book_time` (the market snapshot timestamp). Tickrake stamps `received_at` itself.

Both columns answer "when did our system have this data?" for backtest alignment — named
accurately for their context. A backtest joining across tables uses whichever column is
present on that table.
